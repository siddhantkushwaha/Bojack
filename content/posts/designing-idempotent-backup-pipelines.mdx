Every backup pipeline eventually crashes mid-run. A node dies, a network
partition swallows an ack, a deploy restarts a worker. The question isn't
*whether* you retry — it's whether retrying is **safe**.

"Exactly-once delivery" is mostly a marketing phrase. What you can actually
build is **at-least-once delivery with idempotent processing**, which behaves
like exactly-once from the outside.

## The core idea

Give every unit of work a stable identity — an idempotency key derived from
the input, not from wall-clock time or a random UUID generated at send time.

```go
// The key is a pure function of the input, so a retry produces the same key.
func chunkKey(objectID string, offset int64) string {
    sum := sha256.Sum256([]byte(fmt.Sprintf("%s:%d", objectID, offset)))
    return hex.EncodeToString(sum[:])
}

func (w *Worker) Process(ctx context.Context, chunk Chunk) error {
    key := chunkKey(chunk.ObjectID, chunk.Offset)
    if w.store.Exists(ctx, key) {
        return nil // already durably written; retry is a no-op
    }
    if err := w.store.Put(ctx, key, chunk.Data); err != nil {
        return err // safe to retry: same key, same bytes
    }
    return nil
}
```

Because `chunkKey` is deterministic, a retried chunk lands on the same key. The
`Exists` check turns a duplicate write into a cheap no-op.

## Where people get it wrong

1. **Keys derived from time.** `now()` in the key means every retry is a new
   record. Duplicates guaranteed.
2. **Check-then-write races.** `Exists` followed by `Put` is not atomic. Use a
   conditional write (`PutIfAbsent`) or a unique constraint instead.
3. **Partial writes counted as done.** Only mark work complete *after* the
   durable write returns success.

## A quick reliability model

If a single attempt succeeds with probability $p$, then with independent
retries the probability that the work eventually completes after $n$ attempts
is:

$$
P(\text{done}) = 1 - (1 - p)^n
$$

Even a flaky $p = 0.6$ reaches 99% after just five attempts — *provided* each
attempt is idempotent. Without idempotency, those same five attempts give you
up to five copies of the data.

The lesson: retries are free reliability, but only once your writes stop
caring how many times they happen.
